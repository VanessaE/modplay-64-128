* C128: STOP wedge loader fails on CMD HD over HD/RAMLink parallel.  Same prob  as on C64 with JiffyDOS, but here it only happens if parallel is enabled.
  Disabling parallel with `@P0` before loading my program works around this.

IDEA: at file load time, test the STOP vector before trying to load the MOD
      (but only do it once per device in any given run -- maintain a table
      indicating which device numbers pass the test):
  
  1. read the dir of the device the user's loading from, with pattern
     "$:{ctrl-A}*" (to omit all files and get only the header and blocks free
     message).
  2. Check if there's at least three blocks free
  3. fill the load buffer with some test byte, say $64
  4. save-out the first 761-bytes of it (that's 3 disk blocks minus 1 byte).
  5. zero the buffer
  6. reload the saved file, pointing the STOP vector to a routine that will
     attempt to halt the load after the first page.
  7. Check any byte around the middle of the third page of the load buffer (in
     case the file is being read via C128 BURST protocol).  If it's not 0,
     then the whole file must have been loaded, so mark this drive as
     incompatible with the STOP wedge.  Also do that if the disk was too full
     to allow the file to be created, or if there's any kind of error on load
     or save of the test file.
  8. Close and/or let the load finish, and delete the file.
  9. Load the MOD file as normal, using whichever method the above test
     dictates.
