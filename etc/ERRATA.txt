* Fetch code:  due to lookahead behavior, really short loops tend to get
  kinda "hard-synced" against the REU transfer window, causing pitch
  distortion to the point of sometimes collapsing into just a few discrete
  pitches that bear no relation to the actual requested pitch.

  Possible solution, should be fairly CPU-cheap:

  - in the loop check, calculate how far past the end of the loop the
    lookahead transfer is about to go, and flag it thus (its value being the
    amount of excess, or 0 if there is none).
  - then in the transfer section, I could check that flag, and if necessary,
    grab only the last piece of the sample loop data
  - then fill the remainder of the originally-requested transfer with the data
    from the start of the loop
  - then just set the transfer pointer to the end of that second part, to be
    used on the next go-round

  This would *probably* eliminate the need for unrolling loops as mentioned
  below, though this may still be needed if some random tune really abuses
  the ability of the Paula chip to handle super-short loops.
  
* Loader: Add a mipmap-like feature with filtering.  After the whole file is
  loaded, iterate through the instrument samples, creating downsampled
  versions of each, averaging the sample data at 2:1, 4:1, 8:1, and 16:1
  ratios.  Store the new data all after the end of the original data.

  The rationale here is simple:  at the highest pitches on the slowest
  configurations -- so stock C64 using an REU, in 4-bit SID mode, in stereo,
  with dithering, playing a B-4 note, with the screen enabled -- the REU
  transfer length for the lookahead cache can reach to upwards of 200 bytes.

  Simply switch to the highest ratio (that is, the ratio closest to 1:1) that
  keeps the fetch length at less than 16, and divide the step rate
  accordingly.  The faster the setup, the higher the needed ratio can be.

  This will also allow the program to use a fixed 16-byte fetch length, which
  will trim a few cycles from the lookahead setup code and the fetch/mixer
  code.

  Not only will this likely raise sample rates across the board, it will also
  have the side effect of having properly-averaged the sample data at the
  higher pitches, which should sound a lot better than just skipping over the
  unneded bytes.  Think linear versus nearest neighbor in graphics scaling.

  The only negative side effect is mipmapping will require a bit under twice
  as much expansion RAM, but even at the absolute maximum, counting padding,
  and violating the mod file format by using 128 kB samples, a mod can only be
  up to about 4.4 MB in size, so the most mipmapping could possibly use is
  about 8.5 MB, and 16 MB REUs are commonly available these days.

  That'll rule out using a few of the mods in my testing library on my C128,
  as my REU is just a puny little 1 MB unit.  🙂  Guess I have another reason
  to write the planned SuperCPU RAM driver.  Oh horror. 😉
  
* Loader: all instrument loops need to be unrolled to a minimum length of
  10 kB, which shall be appended to the end of the sample.  That shall then be
  padded with one last copy of the first 1 kB of the loop (or the whole thing
  if it's shorter). If the loop was already over 10 kB, don't do any
  unrolling.  If the loop had to be unrolled, its start and end points shall
  be set to the first and last byte of the newly-unrolled data, excluding that
  last loop copy, and ignoring the original loop data entirely.  If not
  unrolled, the start and end points will remain at their original locations.

  The idea with all this unrolling is to minimize the load on the fetch code
  by requiring fewer loops per second (and hence fewer calls to the code which
  which resets the instrument sample pointer to the loop's start point, which
  is a little expensive).  So-called "chip tunes" are especially problematic
  here, owing to their minimal instrument data (sometimes only a few hundreds
  of bytes, or even less).
