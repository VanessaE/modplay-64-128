##  KNOWN ISSUES  ##
####################

* ALL memory drivers: need to check that file will fit before loading,
  else throw an appropriate error.

* C64/128 BOTH: The STOP wedge loader fails under some odd conditions, such as
  on C64 with JiffyDOS, on C128 with SuperCPU, and C128 with RAMLink if CMD HD
  parallel is available, leading to hangs, crashes, etc. The automatic loader
  selector compensates for these just fine, it just means slower loads than
  should otherwise be possible.

* BOTH: The disk read portions of the loaders need to be decoupled from the
  parts of the code that actually store the data into the expansion RAM, to
  allow for easy manipulation of the data during loading, with predictable
  chunk sizes (most likely, that'll be 256 bytes).

* BOTH: The DMA chip in a standard REU does not know anything about RAM sizes
  greater than 512 kB, due to its limited number of address lines.  As such,
  it can't cross from bank 7 to 8, 15 to 16, etc. when doing a transfer -- it
  just wraps around back to the start of the segment.

  To deal with this, there needs to be some kind of wraparound mitigation in
  the loaders, and it must be done in such a way as to minimize any
  performance impact later when the player's fetch/lookahead/mix code is
  plowing through the instrument data.

  Idea for that:  start each instrument sample right on a page boundary, then
  if a pointer increment puts the store target on page $FE with a bank value
  of (BANK AND 7) = 7, go ahead and store the instrument data into that page
  as normal, bump up to the next bank, copy that page $FE data into this
  bank's page $00, then continue loading from page $01 of this bank. The fetch
  code will of course require similar checks, but without resetting the
  byte/LSB part of the pointer when jumping to the next bank.

  The rationale with this extra copy of the data is that during playback, when
  the fetch code advances to 7/$FE, the lookahead code will most likely have
  already used some of page $FE's data from its previous pass, so we need a
  cheap but seamless transition to the next bank so that the fetch and
  lookahead can continue without skipping any instrument data.

  The C128 memory driver will require a similar mitigation, albeit with
  different boundaries, as the first and last portions of each bank above 0
  are unusable for file data.

* BOTH: all instrument loops need to be unrolled to a minimum length of around
  10 kB, which shall be appended to the end of the sample.  That shall then be
  padded end with one last copy of the first 256 bytes of the loop (or the
  whole thing if it's shorter). If the loop was already over 10 kB, just pad
  the end of the instrument with the first 256 bytes of the loop.  If the loop
  had to be unrolled, its start and end points shall be set to the first and
  last byte of the newly-unrolled data, excluding the final padding and
  ignoring the original loop data.  If not unrolled, its start and endpoints
  remain at their original locations.

* BOTH: on instrument that have no looping, the loader needs to pad the end of
  the instrument with 256 bytes of silence, but the sample endpoint shall
  remain at its original location.

  The idea with all this unrolling and padding is to minimize the load on the
  fetch code by requiring fewer loops per second (and hence fewer calls to
  the code which resets the instrument sample pointer to the loop's start
  point, which is a little expensive).  So-called "chip tunes" are especially
  problematic here, owing to their minimal instrument data (sometimes only a
  few hundreds of bytes, or even less).

  The non-loop padding will also prevent the lookahead code from... well...
  looking so far ahead that it finds either unallocated space or data that
  belongs to the next instrument in the file.  In the case of loops, it
  could potentially run across the instrument data that follows the loop,
  which we don't want either, because that data isn't supposed to be part of
  the loop.  Any of these would end up giving the mixer garbage sample bytes
  on occasion, if left unchecked.
