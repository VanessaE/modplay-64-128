* Fetch code:  due to lookahead behavior, fetching the last bit of a loop
  usually ends up also fetching some amount of the silence at the end of
  each sample, leading to clicks and pops as the sample cycles through the
  loop.

* Sequencer/fetcher/mixer:  need to eliminate that busy-wait that happens
  between the fetcher and mixer -- surely SOMETHING could be run there
  instead of waiting (every cycle spent here is a cycle that can't be used
  for the sequencer, UI, or anything else other than the audio ISR).

  Idea: the sequencer already needs to be converted to run in an IRQ, really
  it's needed this for some time anyway, so do that.

  Make the fetcher and mixer be the "idle loop" or "main loop" or whatever
  it's traditionally called, so that its code runs continuously "underneath"
  the audio and sequencer interrupts:

  - Open main loop
  - CLI
  - do literally ANYthing that can be done here.
  - check for space in the audio ring buffer
    if there's no room, just spin here.
  - SEI
  - run the 16-byte mixer loop to fill up that space
  - CLI
  - do the fetch loop setup
  - do whatever else that can be done here.
  - SEI
  - run the inner fetch loop to update all four tracks.
  - close the main loop, cycle back to the CLI and wait for space.

  In theory, if there were only the CLI and SEI flanking the space check,
  then at worst this could cause up to about a 1400 cycle delay in firing the
  sequencer ISR (150ish cycles of fetch code plus 200 cycles of REU activity,
  times 4 channels), but that's only 0.00142 seconds (PAL), which would be
  completely inaudible.

  In practice, it would be serviced variously during both that interval and
  the interval where the fetch loop setup is run.

  Apart from the actual sequencer code, it will also be this ISR's job to
  scan the keyboard, update the UI, and handle exiting from the player on
  Stop or F7.
    
* Loader: Add a mipmap-like feature with filtering.  After the whole file is
  loaded, iterate through the instrument samples, creating downsampled
  versions of each, averaging the sample data at 2:1, 4:1, 8:1, and 16:1
  ratios.  Store the new data all after the end of the original data.

  The rationale here is simple:  at the highest pitches on the slowest
  configurations -- so stock C64 using an REU, in 4-bit SID mode, in stereo,
  with dithering, playing a B-4 note, with the screen enabled -- the REU
  transfer length for the lookahead cache can reach to upwards of 200 bytes.

  Simply switch to the highest ratio (that is, the ratio closest to 1:1) that
  keeps the fetch length at less than 16, and divide the step rate
  accordingly.  The faster the setup, the higher the needed ratio can be.

  This will also allow the program to use a fixed 16-byte fetch length, which
  will trim a few cycles from the lookahead setup code and the fetch/mixer
  code.

  Not only will this likely raise sample rates across the board, it will also
  have the side effect of having properly-averaged the sample data at the
  higher pitches, which should sound a lot better than just skipping over the
  unneded bytes.  Think linear versus nearest neighbor in graphics scaling.

  The only negative side effect is mipmapping will require a bit under twice
  as much expansion RAM, but even at the absolute maximum, counting padding,
  and violating the mod file format by using 128 kB samples, a mod can only be
  up to about 4.4 MB in size, so the most mipmapping could possibly use is
  about 8.5 MB, and 16 MB REUs are commonly available these days.

  That'll rule out using a few of the mods in my testing library on my C128,
  as my REU is just a puny little 1 MB unit.  🙂  Guess I have another reason
  to write the planned SuperCPU RAM driver.  Oh horror. 😉

  Mipmap outline:

	set "loaded file is mipmapped" to false
	outer_loop:
		fill load buffer with $80
		fetch the next 2 kB of sample data from REU into load buffer,
		or just however much is left.

		next_chunk:
			reset byte pointers

			inner_loop:
				average two bytes of data in the load buffer
				store the resulting byte back into load buffer at origin / 2
				update byte pointers
				repeat 1024, 512, or 256 times,
				returning to inner_loop

				store the resultant 1024/512/256 bytes back to REU at a new place
				bump to next mipmap level, or exit this section
			jump to inner_loop

			repeat until all data for the current sample has been processed
		jump to next_chunk

		advance read pointer to the start of the next sample
	return to outer_loop

	set "loaded file is mipmapped" to true
	exit
