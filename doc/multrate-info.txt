MULTIRATE (decimated sample copies)
===================================

Idea:  the REU fetch length per track per mixer block is proportional to the
note's step rate, so high notes cost a lot of DMA time.  After the load, the
loader builds half- and quarter-rate copies of every sample, and each note
plays from the smallest-numbered copy ("level") at which its step stays within
a fixed fetch window.  Level 0 is the original data and is never touched.

Settings (multirate.s):

                 C64    C128
  window         64     32      MULTIRATE_WINDOW, bytes fetched per track per
                                 block at most (a power of two)
  levels          2      2      MULTIRATE_LEVELS, level L = 1/2^L of the rate

The window caps a block's step at WINDOW/16 bytes per output sample pair.
(Step rates in current_steprates_* are 16x the per-pair step, so the limit
reads as WINDOW.0 in those units.)  Why 64 and 32:  beating was traced to
nearest-neighbor stepping over decimated data with a small step, and the 64
byte window keeps decimated steps large enough to fix it on the C64.  The
C128's higher output rate leaves too little time per block for the REU, and it
sags at 64, so it stays at 32.

Output rates this gives (the ISR interval is the sum of the mixer, driver and
fetch cycle counts plus fudge, see timing-info.txt):

  C64, screen on:   interval 189 cycles (3 rasters, PAL)  = ~5213 Hz
  C128:             interval 97 cycles = ~10.16 kHz PAL, ~10.54 kHz NTSC

Multirate is used only in oldskool builds (no turbo_available).  Turbo builds
assemble the old code paths and never touch any of this.

###############
SETTING AND MODES

multirate_is_allowed is the user's setting:

   0   off:  never resample, play every file in striding mode
   1   on:  resample every file, and refuse a file whose decimated copies
       won't fit in the REU (the "file too large" popup)
   2   on, with fallback:  resample if the copies fit, otherwise play that
       one file in striding mode

multirate_enable is the per-file result, set by the loader for every file:
$80 if this file has decimated copies and uses multirate, 0 if it's in
striding mode.  Everything that matters at playback (the cache layout, the ISR
interval, the level choice at each note) goes by multirate_enable, never by
multirate_is_allowed.  Both are 0 in turbo builds.

Striding mode is the engine as it was before multirate:  each track's cache is
a page of its own, the fetch length follows the note's step rate (up to ~140
bytes at the highest notes), and the mixer steps through the cache at the full
step rate.  See STRIDING MODE below.

###############
TABLES AND MEMORY

Tables are indexed  level*32 + sample  (level 1..MULTIRATE_LEVELS, sample
0..31).  Each table's base address is offset down by 32 so that index 32 is its
first entry.  The level 0 slots don't exist:  level 0 uses the loader's own
tables (sample_start_addresses_*, sample_end_addresses_*, and so on).  There
are no loop-end tables, because for a looped sample the end addr IS the loop
end addr.  Eight tables of MULTIRATE_LEVELS*32 entries:  start mids/highs, end
lows/mids/highs, loop start lows/mids/highs.

The load buffer/sample_data_buffer is LOAD_BUFFER_PAGES (5) pages, 1280 bytes.
Its size is set by the 1084-byte 31-sample MOD header.  The loop unroller works
in chunks of that size, because it stages a whole loop in the buffer, so loops
of 1280 bytes or more aren't unrolled.  Striding mode needs four of its pages
for the caches.

Most of it would have been unused with multirate, so instead we re-use some of
that space for the tables and the module's loader-time variables (~100 bytes),
starting 256 bytes in.  (They end 869 bytes in, and assemble-errs.s checks that
they fit.)

The first page of that buffer holds the live audio cache:  the four tracks'
caches are packed MULTIRATE_WINDOW bytes apart (offsets 0, W, 2W, 3W), which
is why the window is a power of two and why 4 * 64 exactly fills the page on
the C64.  (Turbo builds, and striding mode, keep one page per track.)

The player-side variables (mrp_*) and routines are in the main program area,
because the sequencer code that uses them runs with the ROMs banked out.
current_multirate_levels holds each track's level, and current_loop_start_*
holds each track's loop start for the level it is using (the fetcher restarts
loops from these, not from the loader's tables).


###############
LOADER HOOK (loader-common.s), at the end of the file load

       jsr load_sample_data
       jsr unroll_mod_sample_loops
       multirate_enable = 0                    (assume striding mode)
       if multirate_is_allowed = 0, done
       jsr multirate_generate_all
       if multirate_valid is set, go to fits
       if multirate_is_allowed = 2, done       (fall back to striding mode)
       ... "file too large" popup, jmp abort_load
     fits:
       multirate_enable = $80
     done:

multirate_generate_all returns with multirate_valid = $80 if the decimated
copies fit in the REU.  If they don't, nothing extra has been written and the
tables are invalid.  On success, highest_exp_addresss_used is raised past the
multirate area.


###############
DATA LAYOUT (for checking REU dumps)

Region for (level L, sample S) starts at multirate_sample_start_addresses_*
[L*32+S], page aligned, laid out level by level above the highest expansion
address used by the load, and never crossing a 512k boundary (a region that
would is moved to the next boundary).  It is ceil(source pages / 2^L) + 1
pages long.  Empty sample slots get zeroed entries, with an end address mid
byte of 1.

Contents:  the final (possibly unrolled) level-0 data from the sample start,
decimated L times.  Each decimation step takes a byte pair (a,b) and writes

       m   = (a + b) >> 1
       s   = (s + m + 1) >> 1       running low-pass, carried from page to page,
                                    starts at $80 at the start of each sample
       out = clamp(m + ((m - s) >> 1))

The second line and the third make up for the droop of the 2-tap average (a
one-pole high-frequency boost of 1/2 of m - s).  Level 2 is made from level 1's
output (boost included), with its own filter state.

Looped samples:  loop start = start + (offset >> L), end = loop start +
((loop length + half a decimated sample) >> L), rounding the length to nearest
so that the loop's pitch error is under half a decimated sample.  One extra
source page is decimated for looped samples, so the part beyond the loop end
is there too.

After each level's end addr there are MULTIRATE_GUARD (= MULTIRATE_WINDOW)
bytes, because the fetcher can run that far past the end:  for looped samples,
a copy of the first MULTIRATE_GUARD bytes of the decimated loop, and for
everything else, $80s.  (A decimated loop is never shorter than the window,
because the level-0 loop was already unrolled to at least LOAD_BUFFER_PAGES
pages, 1.25 kB, which is at least 320 bytes at level 2.  assemble-errs.s checks
that this stays at least MULTIRATE_GUARD.)

Note that the loop's length gets rounded to a whole number of decimated
samples, so the pitch error from that is at most half a decimated sample per
loop, or about 2.7 cents for the shortest loop at level 2.


###############
PLAYER SIDE

1. At note start (start_sample -> multirate_apply_level)

   The track's level is set to 0 and the loader's level-0 pointers are
   installed as usual.  multirate_choose_level then picks the level, and for
   level > 0 the track's start pointer (unless the note's command is 9, set
   sample offset, which sets the pointer itself), end address and loop start
   are replaced from the level's tables.

   The level is the smallest one at which the FASTEST pitch the note can reach
   within its row steps by no more than the window.  That pitch is worked out
   from the period and the row's effect:

     0xy  arpeggio             larger of the two semitone offsets
     1xx  slide up             period minus rate * (ticks - 1), min 57
     4xy/6xy  vibrato          period minus 1/16 of itself
     E1x  fine slide up        period minus x

2. Step rate (set_pitch_by_table_lookup -> multirate_shift_steprate)

   Every pitch change, from any command, runs through here with the table-
   lookup step rate in current_steprates_*.  The rate is shifted down by the
   track's level, and clamped to the window.  (In striding mode it does
   nothing at all.)

3. Mid-note promotion (multirate_promote_track)

   The level chosen at note start only covers the current row.  A slide or
   portamento that continues over several rows, vibrato, fine slides, or an
   arpeggio that begins on a later row can take a note past the window.  So
   when the rate, shifted by the track's current level, would exceed the
   window, multirate_shift_steprate moves the note UP one level at a time
   until it fits (or the top level is reached, which is the only place the
   clamp can still act).  Promotion rebases the playing note in place:

     - the position (pointer, 32 bits including the fraction) relative to the
       current level's start is halved, and re-added to the next level's start
     - end address and loop start are replaced by the next level's
     - any pending loop overshoot (current_fetch_loop_ofl_amounts) is halved
     - the level is incremented, and the instrument self-mod routine is run
       so the fetcher gets the new end address

   There is no demotion.  A note sliding down in pitch just runs a smaller
   step over coarser data.

4. Arpeggio

   The arpeggio's two extra notes are made from the base step rate and do not
   pass through multirate_shift_steprate, so multirate_shift_multiplicand_a
   shifts the base rate by the track's level, and multirate_arp_promote
   promotes the note at the arpeggio's start, far enough for the higher extra
   note to fit.  The base pitch is redone if the level changed.

5. Set sample offset (command 9)

   For a track on a decimated copy, the offset is xx*256 >> level bytes into
   that level's copy (multirate_set_sample_offset).


###############
STRIDING MODE

A file plays in striding mode when multirate_enable is 0 (see SETTING AND
MODES).  Oldskool builds have the multirate window built into the fetch loop
and the mixers, so reu_set_cache_layout (drv-reu-musicops.s) sets the engine up
for the file at the start of playback, right after
reu_set_selfmod_and_mixer_vectors.  It always writes everything listed below,
so nothing carries over from the previous file.

                       multirate in use          striding mode
  cache for track n    page 0 of the buffer,     page n of the buffer
                       at n * MULTIRATE_WINDOW
  fetch length         MULTIRATE_WINDOW, fixed   the lookahead distance for the
                                                 track's step rate, patched in
                                                 by the pitch self-mod
  step rate clamp      the window                none
  note levels          0 to MULTIRATE_LEVELS     always 0
  ISR fudge (C128)     15 cycles                 20 cycles

What it patches:

 - the fetch loop's per-track  lda #imm / sta DMA_LOCAL_xx  pair, which stays
   the same size and cycle count:  with multirate, the immediate is the track's
   offset and it's stored in DMA_LOCAL_LO (the page is set once, at the top of
   the routine);  in striding mode, it's the track's cache page and it's stored
   in DMA_LOCAL_HI (the low byte stays 0)
 - the fetch length immediate, which goes back to the window each time
 - mixer_cache_offsets, the per-track starting offsets that the mixers' pitch
   self-mod uses (0, W, 2W, 3W, or all 0)
 - reu_cache_hi_bytes, which supplies the high byte of each of the 16 cache
   reads per track in both mixers

DECIDED AGAINST, FOR NOW

 - A dynamic fetch budget (varying the window per block).  It would cut the
   fraction of notes in Bach Fugue in G-Minor that are played decimated from
   56% to 6%, but it would come at the cost of long DMA bursts and variable
   fetch time.
 - Further changes to sample rates or to the profiler until the Mahoney
   driver has been trimmed and the corresponding bespoke mixers have been
   added.
